# 岛主账户与私人数据方案

> 状态：Draft · 方案已确认，尚未开始开发
>
> 记录日期：2026-10-14

## 1. 目的

Zaizai Isle 将逐渐出现只供岛主本人使用的能力，例如每日学习、私人反馈和人生护照中的长期记录。它们需要一个可跨设备登录、可长期恢复的稳定身份。

项目采用一个预先创建的永久「岛主账户」，作为私人模块的共同身份入口。它不是面向访客的账户系统，也不发展用户注册、角色管理或后台运营平台。

## 2. 账户边界

- 在 Supabase 后台手动创建唯一的邮箱账户。
- 站内提供登录与退出，不提供公开注册入口。
- 账户凭据由密码管理器保管，不写入仓库、前端代码或公开环境变量。
- 数据库维护岛主用户白名单，并通过行级权限校验真实身份；隐藏页面或比较前端邮箱不能替代权限控制。
- 每日学习和人生护照共用同一个岛主身份，但各自的数据表、业务权限和页面状态保持独立。
- 后续私人模块可以复用该身份；是否接入由各模块单独评审。

## 3. 人生护照的双路径

人生护照继续允许任何访客免注册使用：

- **访客路径**：保持匿名身份、私密云端护照、恢复密钥和现有配额逻辑。
- **岛主路径**：使用岛主账户登录，直接访问已授权的私人云端护照，跨设备不依赖浏览器匿名会话。

两条路径使用相同的护照记录与照片模型，不互相公开数据。访客不会被要求注册，岛主登录入口也不改变默认创建护照的流程。

## 4. 岛主现有护照接入

如果岛主已有匿名云端护照，首次接入永久账户时不复制记录：

1. 登录岛主账户。
2. 输入或选择现有护照的恢复密钥。
3. 将岛主用户加入该护照的成员授权。
4. 验证文字、照片、编辑、删除和导出权限。
5. 将这本护照记为岛主账户的默认护照。

恢复密钥继续有效，作为备用访问凭证。第一版不强制转移原始 `owner_id`，成员授权足以建立访问关系；若未来需要所有权转移，另行设计可回滚的迁移。

为避免误建空护照，岛主首次登录后的界面应先询问“接入现有护照”或“创建新护照”，不能在恢复操作之前自动创建默认护照。

## 5. 每日学习

- 每日内容、反馈和私人文字绑定岛主账户。
- 未登录访客不能读取岛主反馈或历史记录。
- 首页可以公开展示模块入口或公共介绍，私人内容仅在登录后出现。
- 每日学习不复用人生护照的恢复密钥，也不写入护照数据结构。

## 6. 会话与安全

- 岛主账户使用独立、持久的 Supabase Auth 会话。
- 人生护照的访客匿名会话继续使用现有独立存储标识；岛主登录、退出不能覆盖访客会话或使匿名护照失联。
- 前端只使用公开客户端密钥；`service_role` 或其他服务端密钥不得进入静态站点。
- 所有私人表和存储对象都必须启用行级权限或等价的服务端校验。
- 岛主授权依据不可由用户自行修改的服务器数据；不使用 `user_metadata`、页面路由或前端显示状态决定权限。
- 登录失败、会话过期和云端保存失败必须明确反馈，不能显示为已保存。

## 7. 实施顺序

1. 在 Supabase 创建岛主账户并取得用户 ID。
2. 建立岛主白名单和服务端身份判断，验证非岛主永久账户与匿名账户均不能访问私人数据。
3. 实现共享的岛主登录、会话读取与退出能力。
4. 先接入人生护照：验证现有匿名路径无回归，再验证恢复密钥授权岛主账户。
5. 再接入每日学习的数据与反馈闭环。
6. 完成真实双设备和隔离会话验证后，才在生产构建中启用。

## 8. 非目标

- 不开放访客注册、登录或社交账户体系。
- 不建设多管理员、角色编辑器或通用管理后台。
- 不自动合并两本护照，也不根据邮箱猜测数据归属。
- 不删除匿名身份与恢复密钥路径。
- 不让岛主账户自动公开私人记录。

## 9. 验收重点

- 岛主可在另一设备登录并访问同一本授权护照和每日学习记录。
- 未登录者、匿名访客及非白名单永久账户不能读取或修改岛主私人数据。
- 访客仍可不登录创建、保存、恢复和使用自己的护照。
- 岛主登录或退出不会覆盖访客匿名会话。
- 现有匿名护照通过恢复密钥接入后不复制、不丢失记录与照片。
- 日志、错误信息与客户端包中不出现密码、恢复密钥或服务端密钥。
