# 人生护照云端部署与验证

> 状态：实现、远端配置和真实联调已完成；生产构建开关待发布时启用。
> 更新：2026-09-29

## 已确认方案

- Next.js 静态前端继续使用 GitHub Pages；用户数据仅在浏览器运行时请求。
- Supabase 匿名登录，独立持久会话，不要求用户注册或提供邮箱。
- 私有数据库与照片桶；护照访问依据设备匿名身份的成员关系。
- 256 位随机恢复密钥，服务器仅保存 SHA-256 摘要。持有密钥可授权另一设备访问；轮换使旧密钥失效，但不会撤销已授权设备。
- 通过主动转存迁移当前 IndexedDB 记录，保留本地原件；同一稳定 ID 不重复导入或覆盖。
- 云端请求失败显示错误，不自动降级成本地保存成功。暂无离线同步队列。

## 服务端限制

| 项目 | 当前限制 |
|---|---|
| 每本护照记录 | 100 枚 |
| 单个照片文件 | 2 MiB |
| 每本护照照片版本预留 | 110 组，每组原图与缩略图各一份 |
| 修改类请求 | 每本护照每分钟 120 次，上传预留/清理也计入 |
| 恢复尝试 | 每个匿名身份每分钟 10 次，失败尝试同样计入 |
| 同一身份关联护照 | 最多 20 本（恢复入口不提供多本管理界面） |

上传先预留不可变路径，两个文件上传完成后才提交记录。编辑使用版本校验，过期编辑/删除被拒绝。替换及删除后的旧文件可清理；失败上传一小时后可回收，在再次访问或保存时尝试清理。清理失败不伪装成内容保存失败，空间仍计入预留上限；后续请求可重试清理。

匿名身份创建受平台 IP 频率限制。以上单护照额度不能替代项目总量监控与防机器人措施。若启用 CAPTCHA，需同步接入前端验证码流程；当前实现不包含验证码组件。不要开启验证码后仍认为匿名创建流程已通过验收。

## 测试与发布门槛

- `npm run test:passport-storage`：原本地数据逻辑回归。
- `npm run test:passport-cloud`：PGlite 上执行迁移，模拟 auth/storage 基础结构，验证私有表访问、跨用户隔离、恢复/轮换/限频、照片不可覆盖、部分上传失败、编辑冲突及配额；另测密钥文件格式。
- `npm run lint`、`npm run build`。
- PGlite 测试不替代线上 Auth、PostgREST 和 Storage 服务联调。线上联调已验证匿名登录、跨用户隔离、恢复密钥、文字保存、照片上传/读取和记录清理；联调护照及两个测试匿名用户已删除，并核对数量均为 0。
- Supabase Security Advisor 在启用匿名登录后标记了项目原有公开表/桶；审计确认相关策略原本即授予 `public`，匿名身份没有新增访问范围。既有 `public.banana_works` 未启用 RLS 的错误与本模块无关，仍需另行治理。
- 使用两个隔离浏览器会话：A 保存含照片与无照片记录；B 无密钥不能访问，输入 A 密钥后可读取和编辑。
- 刷新后恢复身份；下载密钥后清理测试会话，再凭文件恢复。
- 测试断网、失败重试、本地转存中途失败、重复转存、删除及再次导出。
- 检查 SQL 与 Storage advisors，记录原有业务问题及本次新增问题；本次不擅自修改原业务表权限。

## 运行边界

- 恢复密钥文件是访问凭证，不包含文字或照片备份。
- 丢失浏览器身份且没有恢复密钥时，没有邮箱找回流程。
- 在服务器确认保存成功前关闭页面，不能保证尚未提交的编辑已保存。
- 数据库和 Storage 文件需要分别纳入服务端备份策略。
